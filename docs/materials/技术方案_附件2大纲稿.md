## 一、作品概述

### 1. 行业与技术背景
异构智能体协议不一、跨企业/跨云无法互通，是供应链数字化的核心瓶颈。国家 AIP 互联标准与梧桐智能体科研平台提供了注册、发现、安全访问的统一底座。本作品面向工业采购协同，在开源 ACPs/AIP 栈上完成深度二次开发，使采购、供应、物流智能体可在标准协议平面互发现、互调用，并产生可统计的 AMP 访问证据。

### 2. 作品目标定位
- **硬性目标**：六智能体在梧桐平台完成 AIC/ACS 注册；经 ADP 自动发现；经 AIP 跨端 RPC 互联；经 AMP Access/Message 上报，后台可统计访问量。  
- **业务目标**：对话驱动的 10 步采购闭环（发现→HITL 短名单→并行询价→对比三选→议价/竞价→物流合入→双边确认→激活）。  
- **技术指标**：跨云部署（腾讯云采购侧 / 阿里云供应侧）；mTLS；Leader–Partner 编排；双侧 AMP 同 `taskId`/`messageId` 对账。  
- **开源**：遵循 AIP-PUB 生态；鼓励技能与工具在平台分享。

## 二、需求分析

### 1. 行业痛点
协议碎片化、平台适配成本高、跨云证书与身份难统一、访问统计口径不一导致“联了但不可证”。

### 2. 场景与功能需求
| 类别 | 指标 |
|---|---|
| 功能 | ADP 发现、AIP 询价/议价/竞价/物流、HITL 四态门禁、对话编排 |
| 性能 | 并行 3 家询价；发现短 TTL 缓存；演示可 `refresh` 强制打平台 |
| 兼容 | ACS/AIC/ADP/AIP/AMP 报文不改国标结构 |
| 可部署 | systemd + 一键部署脚本；双云 HTTPS RPC |

## 三、技术选型与方案设计

### 1. 基础资源
梧桐 Registry/CA/Discovery；`acps-sdk` / Wit；DeepSeek 对话编排；Kafka `wt.ioa.pub:19092` → `amp.access` / `amp.message`。

### 2. 核心架构
```
业务对话层 (Wit) → 采购编排层 (10 步 + HITL)
       ↓
协议平面 AIC/ACS/ADP/AIP/AMP + mTLS
       ↓
腾讯云：采购A/B + 物流     阿里云：供应A/B/C
```

**二次开发差异（相对标准 demo）**  
1. 跨云异构下的 **双侧 AMP 同 taskId 对账**（买卖双方各记 Access/Message，`messageId=msg-{taskId}`）。  
2. **对话驱动 + HITL 四态门禁**（approve/edit/reject/respond；reject 作废无脏数据）。  
3. ADP **平台优先 + 显式容灾标注**（禁止把本地补齐伪装成平台命中）。

## 四、项目实施

流程：需求拆解 → 开源适配 → AIP 兼容 → 梧桐对接 → 双云联调 → 材料与排行证据。

关键落地：
- 发现：`/acps-adp-v2/discover`；编排层缓存可刷新。  
- 互联：`aip_start_structured` + Partner `/rpc`。  
- 访问：`commerce/amp_log.record_access` 在 Leader `send` 与 Partner `receive` 双侧调用并 Kafka 上报。

## 五、应用成效

### 1. 功能成果
六智能体可被平台发现；采购案可完成并行询价与 HITL；协作面板展示角色/动作/状态/耗时。

### 2. 量化（以联调日志为准，截图进佐证）
- AMP Access / Message 条数、唯一 taskId 数（`GET /api/flow/metrics`）。  
- 发现耗时 `elapsed_ms`、二次发现缓存加速。  
- 询价成功率、HITL reject 阻断率。

### 3. 必要验证场景
| 项 | 状态说明 |
|---|---|
| 注册 | ACS 已提交；AIC 回填服务器 |
| 发现 | ADP 平台路径；材料须截「平台命中」 |
| 互联 | 跨云 AIP RPC |
| 访问 | Kafka AMP；**须附后台访问量截图** |
