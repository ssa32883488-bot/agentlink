# 采销网络 · 双路径互联（需求理解稿）

**日期**：2026-10-30  
**地位**：本项目能立足的两点——① **多智能体互联**；② **人在断点处决断**。  
**范围**：先对齐采购侧发起的两条业务路线；实现另开。

本文是对产品方口述时序的**忠实理解与结构化**，不是旧代码现状说明。

---

## 0. 立足点（三根柱，缺一不可）

| 柱 | 含义 | 在本设计里怎么落地 |
|----|------|-------------------|
| **多智能体互联** | 采购不自嗨；发现走平台，询价/议价/下单/询运走对端智能体接口与共同上下文 | ADP 发现 → AIP（点对点或组群）→ 双方工单用**共同订单标识**对齐确认态 |
| **人在环断点** | 智能体可查、可问、可拟、可建议；**和谁谈、议不议、怎么买、确认单、允不允许找物流**由人拍板 | 断点 = 任务挂起等人；人一确认，状态写入，互联继续 |
| **全员够智力** | 采购聪明不够；供应答不出规格、物流给不出方案，链路在中段断掉，产品不成立 | 每个角色有**可验收的智力清单**；点对点/组群里对端必须能理解意图、查自己的数、组织答复、参与确认 |

采购侧智能体：**理解、改写、联网、解释、建议、代填、建单、缺信息时追问对端**。  
供应 / 物流侧智能体：**听懂采购意图、基于本方主数据作答、报规格/价/政策/运力方案、按接口下单与确认**——不是死表单回显。  
人：**选对象、选是否议价、选买法、确认效力、放行物流**。

### 0.1 「全员够智力」前提（产品硬约束）

> 以上所有交互，**每一个**参与智能体都要有足够智力去应对。  
> 采购问产品规格问不出来、让物流出方案物流给不出来 → **整条采销网络不成立**。  
> 因此：采购智力好，**其他智能体也必须智力好**；分组（采购 AB / 物流 / 三供应）是部署与人设分组，**不是**「只有采购用大模型、其余当脚本」。

按角色的**最低智力水位**（验收用，不是实现细节）：

| 角色 | 必须扛住的智力表现 | 挂了会怎样 |
|------|-------------------|------------|
| **采购 A/B** | 消歧改写、组织发现 query、并行询价/议价话术、比表解释、买法建议、缺物流字段时知道问谁、建单与催确认 | 需求歪、人选错、建议瞎 |
| **供应 A/B/C** | 听懂「要报价/要规格/有无满减/发货时间」；结合**本厂目录·库存·政策**答初报与议价；被追问规格/交期能答；收订单能挂工单并确认 | 步 4/6/10 问规格问空；议价无理由 |
| **物流** | 听懂「我要下运单，先告诉我要什么」；能声明/列出必填字段；收齐后能给出**可执行运力方案**（价/时效/线路级）；能挂单并确认 | 步 9–10 与组群内物流环节瘫痪 |

组群路径额外要求：多方在**同一上下文**里不串话、能针对冲突口径解释己方出价/优惠，物流能在群内把起讫与时间对齐——同样依赖供应与物流的智力，而非采购一个人圆场。

**设计推论**：后续实现供应组、物流组时，与采购 AB **同一档「能对话、能工具、能对主数据负责」的运行时**，禁止「采购 Wit、对端纯 if-else 假答复」冒充互联演示。

## 1. 路线一：普通采购（点对点并行询价 → 议价可选 → 双边确认货单 → 再询运）

### 端到端时序（十步）

```text
用户：「我想采购300套脚轮」
        │
        ▼
【1】理解 + 消歧 + query 改写（对照本智能体画像/库）
     「高端座椅厂 → 重型脚轮」⇒ 完整需求：「采购300套重型脚轮」
        │
        ▼
【2】互联：问梧桐平台（ADP）谁卖重型脚轮 → 返回 n 家 + 各家描述
        │
        ▼
【3】断点① 人选题：带描述的可多选列表 →「确认交互」
        │  （人未确认前，不向任何供应发询价）
        ▼
【4】互联：对勾选的每一家并行询价
     话术级意图：「我需要300套重型脚轮，请给我报价」
     回收：初报 + 规格 → 表格给人 + 智能体解释
        │
        ▼
【5】断点② 人选题：要不要议价（探优惠/满减/折扣）
        │
        ├─ 不议价 ─────────────────────────────────┐
        ▼ 议价                                      │
【6】互联：带着更大/更明确的采购意图再问对端         │
     例：「拟采500套重型脚轮，有无优惠；有则理由+优惠价； │
          无则原始价；要含规格与发货时间」              │
     回收后：议价前后对比表 +「怎么买最划算」建议       │
        │                                           │
        ▼◄──────────────────────────────────────────┘
【7】断点③ 人决断怎么买（可含推荐）
     例：300 不满足满500九折 → 仍下300 / 加到500拿折扣 / Other
        │
        ▼
【8】效力最大的下单意图锁定（数量、对象、价格逻辑已定）
     · 采购侧创建订单工单 → 提醒人去工单点确认
     · 按对端下单接口下单 + 双方共享唯一订单标识
     · 仅当双方都确认 → 货物订单完结（生效）
        │
        ▼
【9】建议去询物流；人允许后 → 问物流智能体「下运单要什么」
     物流答：总规格、起讫地、出库发货时间…
        │
        ▼
【10】缺什么就补什么（优先历史；缺规格/发货时间则主动问供应）
      凑齐后走物流下单接口 → 再双边确认 → 物流工单完结
```

### 三个「人断点」对照（普通路径）

| 断点 | 步 | 人决定什么 | 智能体此时不该做什么 |
|------|----|------------|----------------------|
| ① | 3 | 和**哪些**供应智能体交互（可多选） | 未勾选就发询价 |
| ② | 5 | **要不要**探优惠/议价 | 擅自二次询价或跳过优惠探测 |
| ③ | 7 | **怎么买**（数量/对象/是否吃满减；可 Other） | 替人锁定最终买法 |

另有两类**确认闸**（效力，不是选题）：

| 闸 | 步 | 含义 |
|----|----|------|
| 货单双边确认 | 8 | 共同订单标识下，采购确认 + 供应确认 → 货单完结 |
| 物流双边确认 | 10 | 物流单同样双边确认 → 运单完结 |

步 9「允不允许去找物流」是**放行**，介于建议与闸之间：人允许后才开始问物流要字段。

### 普通路径里的「互联」发生点

| 步 | 对谁 | 干什么 |
|----|------|--------|
| 2 | 梧桐平台 | 发现：谁符合「售卖重型脚轮」 |
| 4 | 人选中的供应（并行） | 初轮询价 |
| 6 | 人选中要议价的供应 | 优惠/满减探测 |
| 8 | 最终下单对象 | 下单接口 + 共享订单标识 + 确认态 |
| 9–10 | 物流；必要时回供应 | 询运字段、补规格/发货时间、物流下单 + 确认 |

### 理解要点（我确认已对齐）

1. **Query 改写是采购智能体的职责**：用户说「脚轮」，画像是高端座椅 → 改写成「重型脚轮」再去发现；不是把口语原样丢给平台。  
2. **发现结果对人可见、由人圈定交互对象**：平台返回 n 家 ≠ 自动全员询价。  
3. **初报与议价是两轮互联**：第二轮专门解决「对面有没有政策」的信息差。  
4. **最终买法可以和首轮数量不一致**（300→500 吃满减），这是断点③的意义。  
5. **订单效力 = 双方确认 + 唯一共享标识**，不是对话里说「我下了」。  
6. **物流是货单生效后的下一程**：先问物流要什么，缺了再向供应补齐，再下运单并双边确认；不与货价询价搅在同一轮里自动完成。

## 2. 路线二：组群竞价（采购主持 · 共同上下文 · 多方出价 · 人决断 · 群内定物流）

### 钉死规则

| 项 | 约定 |
|----|------|
| **主持** | **必须有主持；主持 = 采购智能体本身**（开群、维持共同上下文、收束出价、提请人决断、推动出单） |
| **入群前** | **必须再走断点①**：人决定**是否进行组群竞价**并勾选参与对象；未获人确认不得开群拉人 |
| **冲突/复杂** | 采购根据需求复杂度与问询回包冲突**建议**组群；是否开群由人在断点①拍板 |

### 时序理解

```text
复杂需求 / 回包冲突 → 采购建议组群
        │
        ▼
【断点①】人决定：是否组群竞价 + 勾选参与智能体
        │  （否 → 回普通路径或停止；是 → 开群）
        ▼
采购主持开群：入选供应（+ 后续物流）进入**同一共同上下文**
        │
        ▼
各方在群里出价、报优惠、对齐口径（主持维持秩序与上下文）
        │
        ▼
断点：人决断和谁下单、下哪些单（主持整理选项给人）
        │
        ▼
物流在群聊里把运力/线路/时间等细节谈清（主持收束）
        │
        ▼
形成**一系列**待办工单 → 各方确认 → 完结
```

### 与普通路径的本质差别

| | 普通采购 | 组群竞价 |
|--|----------|----------|
| 上下文 | 多条点对点 | **共享群上下文**，**采购主持** |
| 价格形成 | 初报 →（可选）议价 → 人选买法 | 群内出价/优惠，人一次决断 |
| 物流 | 货单后另询运 | **群内**谈清再出系列工单 |
| 工单形态 | 货单 + 物流单 | **一系列**工单多方确认 |
| 入场 | 断点①选交互对象后并行询价 | 断点①选**是否组群**+成员后主持开群 |

### 组群路径上的人断点

- **断点①（入场）**：是否组群竞价 + 谁入群。  
- **主决断**：群内出价后和谁下哪些单。  
- **确认闸**：系列工单各方确认。

## 3. 两条路线如何共用「立足点」

```text
                    梧桐平台（发现）
                         │
            ┌────────────┴────────────┐
            ▼                         ▼
     普通：点对点并行              组群：共同上下文
     询价→议价→下单               出价→人决→群内物流
            │                         │
            └────────────┬────────────┘
                         ▼
              共享订单标识 + 双边/多方确认工单
                         │
                         ▼
                    人：断点决断 + 确认效力
```

- **互联**：没有平台发现与对端接口/组群，就只是单机聊天。  
- **人断点**：没有①②③（及组群决断）与双边确认，智能体就会替人做生意或「嘴上确认」。

## 4. 与「Ask vs Gate」的贴合（便于后序设计）

| 产品断点 | 机制归类 |
|----------|----------|
| 选哪些智能体交互 / 是否组群 | 人断点① → **选题/多选**（普通=确认交互；组群=是否竞价+成员） |
| 要不要议价 | 人断点② → **AskUser** |
| 怎么买（300/500/Other） | 人断点③ → **AskUser** |
| 工单点确认 | **Gate**（效力） |
| 允许去找物流 | **放行 Gate** |
| 组群里和谁下单 | **AskUser / 决断面板**（主持整理） |
| 系列工单各方确认 | **Gate** |

## 5. 已钉死 / 仍可后定

### 已钉死

| 项 | 结论 |
|----|------|
| 组群主持 | **采购智能体本人** |
| 入群前断点① | **要**；人决定是否组群竞价并勾选成员 |
| 智力验收 | **按 §0.1 角色最低水位表**作为可测标准（规格问得出、方案给得出…） |
| 与旧实现关系 | **旧业务实现全部切割、一点不留**；**保留核心 ACPs 协议能力**（ADP/AIP/AMP、注册/证书/RPC 等），在协议之上从零搭建业务 |
| 采购 A/B | 共用十步+组群契约；仅画像/默认改写不同 |
| 断点②选不议价 | 直接基于初报进断点③ |

### 动手前三条细则（已妥善约定）

#### A. 「冲突」机器信号（采购据此**建议**组群；开群仍须断点①）

满足 **任一** 即可建议组群（可多信号叠加加权展示理由）：

| # | 信号 | 可检含义（示例） |
|---|------|------------------|
| C1 | **口径冲突** | ≥2 家回包对同一关键属性不一致（承重档/材质/可否供该 SKU/交期单位等） |
| C2 | **可比性不足** | 初报字段集合交叉过小，无法做成同一张比价表（缺共同维度） |
| C3 | **需求复合** | Case.brief 含 ≥2 条异构物料线，且短名单内没有单家能完整覆盖 |
| C4 | **政策不可比** | 各家优惠门槛/计量口径互斥（满件 vs 满额 vs 无政策），议价话术无法统一 |
| C5 | **人显式要求** | 用户直接说要竞价/比着买/拉群谈（最高优先级建议） |

**不建议组群**：仅 1 家可供；或各家回包口径一致且单表可比。  
**效力**：信号只驱动「采购提议组群 + 说明理由」；**不得**跳过断点①自动开群。

#### B. 物流字段：清单为主，追问为辅（并存）

```text
1. 物流智能体暴露「运单必填清单」（能力/接口声明）
   默认项：货物规格摘要、计费相关量（重量或体积或件数口径）、起运地、到达地、期望出库/发货时间
2. 采购按清单对账：历史 Case/货单/供应回包里能填的先填
3. 仍缺 → 定向追问持有方（规格/发货时间优先问供应；起讫地问人或用采购商档案默认）
4. 人放行询运后，才把凑齐的字段提交物流下单/要方案
```

禁止：无清单瞎聊到永远；也禁止清单外字段阻塞下单（额外字段仅优化方案，非必填）。

#### C. 组群中物流何时入群

**约定：货意向清后再拉物流（不开群就进）。**

```text
断点① 人确认组群并选供应 → 采购主持开群（成员=入选供应）
        → 群内出价/优惠/对齐
        → 人决断：和谁、下哪些货单
        → 【此时】主持邀请物流入群
        → 群内谈运力/线路/时间（可对已决供方与起讫）
        → 出系列工单（货 + 运）→ 各方确认
```

| 何时 | 做不做 |
|------|--------|
| 开群当时 | **不**拉物流（避免无货意向时空谈运价） |
| 人决断下单对象之后、出系列工单之前 | **拉**物流入群谈细节 |
| 普通路径 | 不走入群；货单生效 → 人放行 → 清单对账 → 点对点询运/下单 |

## 6. 工程切割边界（根上约定）

```text
保留：ACPs 协议层与平台接入
  · ADP 发现 / AIP 任务与组群 / AMP
  · AIC·ACS·证书·mTLS·/rpc 等已对齐梧桐的部分

切开丢弃：旧采销业务楼（编排、伪 HITL、旧 flow/工单粘合、套皮 AskUser 业务逻辑等）
  · 在协议之上按本文双路径 + 三柱 + 全员智力 重搭
```

## 7. 一句话复述（验收我是否听懂）

**普通路径**：改写需求 → 平台发现 → **人圈定对象** → 并行初报 → **人决定是否议价** →（议价则）对比建议 → **人决定怎么买** → 共享标识下单并**双方确认货单** → 人放行后问物流要字段、缺则问供应 → 物流下单并**双方确认**。  

**组群路径**：复杂/冲突 → 采购**建议** → **人断点①确认是否组群并选成员** → **采购主持**开共同上下文 → 多方出价 → **人决断和谁下哪些单** → 物流在群内对齐 → **系列工单多方确认**。  

项目靠三根柱立住：**协议上的互联**、**断点上的人**、**采购·供应·物流全员够智力**。  
旧业务全切；**ACPs 核心保留**；对端答不出规格、给不出运力方案，等于没有互联。
