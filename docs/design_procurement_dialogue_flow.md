# 采购全流程对答 · 业务流固化（目标态）

> 来源：产品图「全流程对答」+ 运营六阶段解释（2026-10-26 确认）  
> 地位：重构目标业务真相；与当前 as-built（单品三家整案）对照，不表示已全部落地。  
> 原则：采购智能体 A = 编排/计算/并行谈判；运营人员 = HITL 闸门；销售 = 货+自报运费；物流 Agent = 可呼叫的运费重计价器。

---

## 1. 业务一句话

**多零件组合采购**：并行向多家销售询价（货+运）→ 结构化比价 → 人下令议价 → 按政策重算 → 推出单供/凑单/跨企+物流统调等方案 → 人选方案 → 拆多订单并分摊运费 → 人确认支付履约。

---

## 2. 角色

| 角色 | 类型 | 职责 |
|---|---|---|
| 运营人员 | 人类 | 发起/调整意图；下令议价；选定方案；确认支付/发货 |
| 采购智能体 A | Leader Agent | 发需求、并行询/议价、结构化、方案推演、拆单、呼叫物流 |
| 销售 A/B/C | Partner Agent | 报价（零件价+自报运费）、折扣/满减/免运政策 |
| 物流 Agent | Partner Agent | **不由采购 A 直接发现**（V1）；由**供应商**在报价路径上被动发现并询运费，将「货+运」一并回给采购 |

地理示例（图中）：采购侧河北保定；销售沧州/邢台/太原（距离影响运费）。

### 2.1 V1 发现权责（已拍板）

| 能力 | 装在谁身上 | 形态 |
|---|---|---|
| `discover.suppliers` | **采购智能体 A** | 主动 Tool：需要找供应商时调 ADP |
| `discover.logistics` | **供应商智能体**（A/B/C） | **被动技能**：收到采购初步询价时自动触发，找合适物流并询运况 |
| 采购侧 `discover.logistics` | **V1 不装** | 降低首版复杂度；跨企统调（原方案 S3 采购直接呼物流）列为后期 |

**供应商报价路径（V1）**

```
采购 --AIP 询价--> 供应商
                      ├─（被动）discover.logistics → ADP 找物流
                      ├─ AIP 询物流运费/时效
                      └─ 回执：零件价 + 运费(+距离/时效等) 一并交给采购
```

采购 A 首轮拿到的已是各销售侧的 **货+运捆包总价**，不必自己先发现物流。

## 3. 需求与报价对象（数据最小集）

### 3.1 采购需求（可多行）

| 字段 | 示例 |
|---|---|
| 行项目 | 零件 a × 100；零件 b × 500 |
| 交期/质量约束 | （图中可扩展） |
| 收货地 | 保定（影响距离与物流） |

### 3.2 销售初始报价（按供应商一份）

| 字段 | 含义 |
|---|---|
| 各零件单价 | a、b 单价 |
| 销售自报运费 | 与距离绑定的捆包运费 |
| 满减/活动 | 如 b 满足满减 |
| 距离 / 发货速度 | 比价维度 |
| 货价小计 + 运费 → **销售侧总价** | 决策用 TCO（议价前） |

### 3.3 议价政策（可能改变采购量）

| 类型 | 示例 | 计算要点 |
|---|---|---|
| **满减（三家均有）** | 沧州满货价1.2万减500；邢台满300件减4%；太原满1万减450 | 可能需 **加量** 才踩门槛；必须展示「加量后总支出 / 净增」 |
| **跨省补贴（仅山西太原）** | 出省运费补贴约 35%，满 150 件可申请 | **审核不确定**；适合预算宽裕、愿沟通的路径 |
| 善意单价让步 | 议价仅小幅让价（约 1%） | **禁止**把议价做成单纯压单价 |
| （扩展）账期/交期交换 | — | 进方案维度，非必须首期 |

**预算规则**：预算 **不是** 采购商必须交代的内容；智能体默认返回多方案。若人自愿说「紧/宽裕」，仅用于方案排序标签，**永不**出站给供应商。

### 3.4 物流统调结果

| 字段 | 含义 |
|---|---|
| 总运费 | 物流 Agent 统调价（可显著低于分家自报运费之和） |
| 分摊到各拆单 | 如订单 A 300 + 订单 B 700 = 1000 |

## 4. 六阶段主流程（固化）

```
[人] 确认/发起组合需求
        ↓
① 采购A → 并行询价 销售A/B/C（货+自报运费）
        ↓
② 采购A 内部结构化：多维对比表 → 推送给运营
        ↓
③ [HITL-1] 运营：「可以，去谈谈折扣优惠」
        ↓
   采购A 并行议价 A/B/C → 按政策重算各家总价（含加量代价）
        ↓
④ 采购A 汇总 + 生成方案空间（≥3 类，见下）→ 推送运营
        ↓
⑤ [HITL-2] 运营选定方案（如组合方案3）
        ↓
   采购A：拆单创建 +（若方案含物流统调）呼叫物流Agent → 运费分摊展示
        ↓
⑥ [HITL-3] 运营确认支付/发货 → 履约闭环
```

### 阶段细节

**① 需求发起与初始询价**  
- 采购 A 发出组合需求（a100+b500）。  
- 销售各回：单价、运费、距离、（可选）满减 → 算出销售侧总价。  
- 图例量级：B 初始总价最低；C 因运费总价最高。

**② 内部结构化**  
- 生成对比表（距离、速度、单价、折扣/活动、运费、总价）。  
- **推人**，不自动成交。

**③ 人下令议价 → 并行谈判**  
- 人只给意图，不替 Agent 填每家话术细节（可由 Agent 生成合规问法）。  
- 各家政策不同 → **必须重算**；识别「折扣导致总支出变高」（如 B）。  
- C 类免运可使总价大幅下降。

**④ 方案推演（固化三类，可扩展）**

| 方案类型 | 含义 | 图例 |
|---|---|---|
| S1 单供应商·现量 | 选一家、维持需求量 | 吃已触发满减；预算中性默认项 |
| S2 凑满减 / 冲跨省补贴 | 加量踩门槛；山西补贴带不确定性 | 预算 **宽裕** 时可优先讨论 |
| S3 拆单分采 | 按库存/成本拆两家（如山西能供多少拿多少 + 河北补缺口） | 预算 **偏紧** 或不想加量时；V1 用各家自带运费（物流统调后期） |

**⑤ 人选方案 → 落单**  
- S3：分别建订单 A、订单 B；展示货价 + **分摊运费**；提示统调节省。  
- 等待人最终确认。

**⑥ 支付与履约门禁**  
- 「两单确认无误，是否支付并生成发货单？」→ 人确认后才进入支付/发货。

---

## 5. HITL 闸门（强制）

| 编号 | 触发点 | 人做什么 | Agent 禁止 |
|---|---|---|---|
| H1 | 初始比价后 | 是否议价、议价目标口径 | 未授权自动议价 |
| H2 | 方案列表后 | 选定 S1/S2/S3（或改条件） | 未选定自动拆单下单 |
| H3 | 多订单+运费展示后 | 是否支付/发货 | 未确认自动支付 |

（可选 H0：需求内容确认；可选 H-reject：作废本案。）

---

## 6. 不变式（实现时必须守住）

1. **TCO 口径**：比较必须含运费；销售自报运费与物流统调运费要分列，不可混成一个「运费」糊弄人。  
2. **门槛代价**：折扣/免运若要求加量，方案与回复必须展示「加量后总支出」，避免假便宜。  
3. **并行谈判**：对 A/B/C 的询价、议价默认可并行；汇总后再推人。  
4. **供应商隔离**：甲的原文报价/政策细节不传给乙；人侧只看汇总与方案。  
5. **物流发现在供应侧（V1）**：采购不发现物流；供应商报价前被动 `discover.logistics` + 询运，回「货+运」。物流仍是平台上的独立 Agent，只是 **调用方是供应商**。  
6. **拆单一致性**（启用 S3 时）：多订单 + 运费分摊；V1 可先不实现采购侧统调。  
7. **平台发现**：供应商/物流均经 ADP；找不到就是没有（无本地黄页兜底）。

## 7. 与当前 as-built 对照（差距清单）

| 目标态 | 当前近似 | 缺口 |
|---|---|---|
| 多行零件需求 | 单 `product_name`+qty | 行项目模型 |
| 销售侧货+运报价 | 多为货价，物流后置合入 | 询价 schema 含自报运费/距离 |
| 议价政策+加量重算 | 有议价轮，弱政策/门槛 | 政策结构化与重算引擎 |
| S1/S2/S3 方案空间 | 基本「选一家」 | 方案生成器 |
| 跨企拆单 | 无 | 多订单 |
| 物流统调分摊 | 单次 shipping 合入一单 | 物流 Agent 统调 API + 分摊 |
| H1/H2/H3 | 有短名单/激活等门禁 | 对齐本流三道 HITL |

## 8. 采购智能体 A · V1 Tools 目录（已拍板）

### 8.1 协议协作类

#### `discover.suppliers`
- **何时**：Agent 确认需要找供应商时调用。  
- **做什么**：向梧桐平台 ADP 发起匹配请求 → 平台返回候选 → **本侧初步筛选**，保留最合适的若干家 → 返回并持久化 **结构化候选**（aic、名称、endpoint、skills、匹配理由等）。  
- **对人**：结构化数据由 **UI 渲染为可交互表单**，供用户勾选确认（Tool 负责出数与落库，不负责画 UI）。  
- **不做**：询价；本地 ACS 兜底。

#### `rfq.send_batch`
- **何时**：用户已在表单中确认短名单之后。  
- **入参**：用户选中的智能体列表（1–5 家）。  
- **做什么**：对选中对象 **并行** 发起询价请求；**等全部返回**（或超时策略）后，将结果 **拼接** 为一次 Tool 输出。  
- **并行度**：固定范围 **1–5**。  
- **回执口径**：各家 **货+运** 捆包报价（物流由供应商被动发现，采购不调物流）。

#### `partner.dialog`（询价/议价/按需问价 · 统一对话接口）
- **理解**：专门与 **已筛选/已入短名单** 的智能体通信的 AIP 通道。  
- **覆盖**：初步定向追问、议价、按自身需求改量问价、澄清等——**同一 Tool**，用 `intent` + payload 区分，不设 `ask_policy` / `requote` 并列工具。  
- **与 `rfq.send_batch` 关系**：  
  - `rfq.send_batch` = **首轮、对人确认后的并行询价专用**（多路等待+拼接）；  
  - `partner.dialog` = **其后与单家（或按需）深入对话**；若要对多家再谈一轮，可由 Agent 多次调用或后续再加薄封装 `dialog_batch`（V1 可不做）。  
- **底层**：二者都走「记住的 endpoint」，不是两套协议。

#### 明确不装（采购 V1）
- `discover.logistics`、物流统筹 Tool —— 物流环节在供应商侧。

```
discover.suppliers → 结构化候选 → [UI 表单 HITL 勾选]
       ↓
rfq.send_batch(选中 1–5) → 并行询价 → 拼接报价表
       ↓
[HITL 议价意图等]
       ↓
partner.dialog(intent=negotiate|clarify|…) → 深入谈
```

### 8.2 本地业务类

面向本厂运营数据（非跨企业 AIP），示例：

| Tool | 用途 |
|---|---|
| `erp.query_inventory` | 库存 / 安全线 |
| `erp.query_orders` | 销售单 / 采购单（可再拆） |
| `erp.query_notifications` | 通知 |
| （按需）`erp.query_db` / 只读报表 | 受控本地库查询（须鉴权与表白名单） |

### 8.3 记忆类

| Tool | 用途 |
|---|---|
| `memory.inject` | 注入本轮/本案要记住的约束（收货地、偏好、人已确认选项） |
| `memory.extract` | 按本案/会话提取已记关键信息 |
| `memory.record` | 记录关键事实节点（短名单、报价快照 id、所选方案等）供审计与后续规划 |

记忆落在 **案件/会话存储**，不替代 `discover`/`rfq` 的结构化结果；模型不得假装「记住了」却未调 memory/业务落库。

### 8.4 计算类（建议保留，可对模型暴露或仅供内部）

| Tool / 引擎 | 用途 |
|---|---|
| `calc.compare_table` | 把 batch/dialog 回执收成对比表 |
| `plan.propose` | S1/S2（S3 后期）方案推演 |
